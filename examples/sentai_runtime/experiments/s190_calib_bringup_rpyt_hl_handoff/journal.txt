KEY FINDING — PnP-Z perspective bias is a HARD blocker:

Drone is at REAL altitude ~2 m (ekf_z reads 2.31, GT not captured this
run but iter-3 GT confirmed ~7 m when ekf said 7.66 — consistent).
But PnP says z=0.008 m.  ~290× off.

This is the Krajník depth-from-ring perspective bias — the formula
`z = fx * D / (2 * axis_a) * ANNULUS_FACTOR` is very sensitive to
measured `axis_a` (semi-major of ring), which is affected by perspective
when marker is off image center.

Feeding ExtPos with biased z=0.008 to cf2 → Kalman believes drone is
~0 m → controller commands extreme thrust to "reach Z_HOLD=0.6 m" from
"current 0" → drone climbs more → markers shrink → PnP gets worse →
runaway loop → SAFETY abort by orchestrator.

NEXT STEP: W21-T8 (coplanar multi-marker pixel PnP) is now the
critical path — without unbiased PnP-z, no further iteration on
ramp parameters helps.  Either implement coplanar pixel-PnP
(DLT/homography on plane, ~100-200 LoC C++), OR use a different
position-injection strategy (e.g., XY-only).

artifacts: mission_s190_journal.txt (170 ramp_tick rows + handoff +

## iter-14..20 (2026-05-22 11:30-12:00)  PD ALTITUDE HOLD via vision

User-stated direction: "cumva redu thrust co cresterea lui Z asa incat
cu cat creste mai mult cu atat sa ii scazi acceleratia. Pana cand Z
nu mai creste".  This is the classic quadrotor PD altitude controller
(Bouabdallah 2004, Mahony/Kumar/Corke 2012).

Mass + motor pulled from SDF:
- m = 0.025 (base) + 4·0.0008 (props) = 0.0282 kg
- F_max = 4·motorConstant·maxRotVelocity² = 4·1.8145e-8·3052² = 0.676 N
- F_hover = m·g = 0.277 N
- T_hover_predicted = 65535·sqrt(0.277/0.676) ≈ 41900 thrust units
- Empirical T_hover ≈ 36000 (CrazySim plugin diverges from formula 15%)
- dF/dT @ hover (linear) ≈ 1.1e-5 N/unit

Physics-tuned PD (ω_n=1.5 rad/s, ζ=0.8 critically damped):
  Kp = m·ω_n²/(dF/dT) ≈ 6000 units/m
  Kd = 1.6·m·ω_n/(dF/dT) ≈ 6000 units/(m/s)
