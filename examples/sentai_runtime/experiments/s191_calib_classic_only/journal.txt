## What we LEARNED across iter-1..6

1. **PnP yaw is unreliable** — flips between mirror solutions per
   frame.  Cannot use for yaw lock or for body→world rotation.
   Future: use cf2 gyro yaw (sentai.crazy.pose()[3]) OR add hysteresis.

2. **Axis identification is REQUIRED** — pitch/roll → X/Y mapping
   is NOT identity.  May be swapped, may have wrong sign.
   Calibration must DETERMINE this in-flight via test pulses.

3. **Gentle gains AT FIRST** — operator-stated: "miscari foarte mici"
   for axis ID, otherwise destabilize.  Recovery requires OPPOSITE
   pulse to return drone to start.

4. **Phase4 → Phase5 transition has residual velocity** — drone
   carries momentum into XY hold.  Need to damp velocity BEFORE
   testing axis sign.

## iter-19 (2026-05-22 18:30)  DETECTOR UNDER-COUNT — root cause found

Operator-stated: "verifica pe cateva frames random din zbor, cati
markeri a detectat algoritmul si cati sunt de fapt in poza".

Method:
1. PGM frames saved by sentai.fr at 30Hz during iter-18 (242 frames).
2. Filename encodes algorithm's n_dets: `t<ms>_n<n_dets>_f<seq>.pgm`.
3. Independent OpenCV blob-count (threshold 80, circularity > 0.4)
   on 15 random in-flight frames.
4. Visual inspection of representative frames per n_dets bucket.

Findings:
- Algorithm reports n_dets ∈ {0, 2, 3, 4, 5, 6} across iter-18 flight.
- 131/242 frames had n_dets=0 (drone landed or markers OOF — verified
  cv_count=0 on all sampled n=0 frames).
- 2 of 15 random in-flight samples showed CONFIRMED under-count:
  algorithm 4, OpenCV 6.  Visual inspection: all 6 markers clearly
  visible.

Instrumented detector (sentai_aruco.cc line 2809) to log per-frame
reject distribution on under-count cases.  Iter-19 re-run:
- 148/151 in-flight frames have n_comp ≥ 4 with accepted < n_comp.
- Reject reason ranking (per-frame frequency, descending):
  * min_area: dominant (~60% — mostly noise blobs, OK to reject)
  * border:   ~50% — markers near frame edge (drone tilt during
              axis ID pulses shifts FOV → markers clipped)
  * axis:     ~50% — eigenvalue ratio > 2.0
  * ar:       ~30% — bbox aspect > 2.0
  * fill:     ~25% — fill ratio < 0.40
  * w3:       ~10% — concentric check rejects (somehow enabled?)

Most common pattern: n_comp=96 acc=5 border=13 ar=6 fill=4 axis=2 w3=3.
6 markers visible → algorithm gets 5 → PnP solves on 5-marker subset.
Different frame: same scene, same 6 markers → algorithm gets 4 →
PnP solves on different 4-marker subset → different X/Y solution.

This IS the "PnP bimodal" root cause — not yaw_anchor mirror picker,
but UNSTABLE DETECTION COUNT.  Marker SET varies per-frame, PnP
rebuilds each frame on different subset.

Saved 5 sample frames + 2 OpenCV-annotated mismatches under
marker_analysis/.

Fix plan iter-20:
1. min_area 40→20 (allow distant markers).
2. border rule: instead of rejecting touch, only reject if blob's
   bbox extends > N pixels beyond detection region (i.e., we have a
   FULL view of the blob).  Markers WITHIN the frame but adjacent
   to its boundary are still valid.
3. max_bbox_ar 2.0→2.5 (slightly elongated due to perspective).

### Phase 1 — Refactor
Generic helpers renamed from `aruco_*` to `markers_*` (shared between
ArUco + WhyCon detectors).  ArUco-specific code (extract_quad,
decode, ippe_*) stays `aruco_*`.

### Phase 2 — OpenCV-equivalent metrics
Added in sentai_aruco.cc:
  - `markers_arc_length`        — chain-code perimeter
                                   (cv2.arcLength equivalent)
  - `markers_contour_area`      — shoelace formula on contour
                                   (cv2.contourArea equivalent)
  - `markers_circularity`       — 4π·A/P²
                                   (cv2 standard ring metric)
  - `markers_contour_centroid`  — polygon centroid (Green's theorem)
                                   on outer contour (sub-pixel)
  - `whycon_adaptive_threshold_` — cv2.adaptiveThreshold with
                                    MEAN_C, THRESH_BINARY_INV
                                    semantics; block=11, C=4 default
                                    (cv2 standard for ring markers).

`whycon_filter_and_moments_` updated:
  - REMOVED: `fill = n_pix/bbox_area` metric (sat at 0.40 threshold
              for typical rings — slight perspective dropped real
              markers).
  - ADDED:   Moore-Neighbor outer-contour trace + circularity check
              + contour-based sub-pixel centroid.

### Phase 3 — 1:1 verification harness
`marker_analysis/compare_v2.py` runs our detector via REPL
(sentai.markers.detect_buffer) and cv2.findContours side-by-side
on 10 random PGM frames.  Frame copied into fs_root as
`_test_frame.pgm`, detected via `import detect_pgm; detect_pgm.run()`.

### Frame analysis
- Low-altitude (~0.8m), 6-marker view: 6/6 to 6/7 match — close to perfect.
- High-altitude (~2.5m), 6 markers visible: 2/6 — Moore-Neighbor
  staircase noise on 10-15px blobs drops circularity below 0.55.
- Close range (markers > 60px each): cv rejects all but 1 via
  max_area=4000 — we catch them all because our threshold splits
  rings into smaller blobs.
