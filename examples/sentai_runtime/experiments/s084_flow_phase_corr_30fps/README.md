# s084_flow_phase_corr_30fps

On-board phase-correlation optical flow validation, **build #1139**, full
sensor rate (30 fps), operator-protocol square walk.

## Result headline

| Metric | Value |
|---|---|
| Algorithm | Phase correlation (FFT2 64x64 + Tukey + Foroosh sub-pixel) |
| Effective rate | 29.97 fps |
| Frame pairs | 479 over 16.0 s |
| MOVE conf avg | 213.6 (range 0..255) |
| MOVE stuck<0.05 | 13.7% |
| HOLD conf avg | 233.9 |
| HOLD stuck<0.05 | 11.7% |
| **Closure error** | **51 raw-px** (6.39 grid-px) |

## Comparison

| Run | Algo | fps | Closure (raw-px) |
|---|---|---|---|
| s083 | SAD validated | 15 | 74 |
| #1123 | SAD | 30 | 350 (degraded) |
| #1124 | SAD + rate-aware deadband | 30 | 650 |
| #1125 | SAD rollback | 15 | 55 |
| **s084 / #1139** | **Phase correlation** | **30** | **51** |

Phase correlation at 30 fps **beats SAD at 15 fps**. SAD degrades sharply
above 15 fps because block-matching sub-pixel accuracy collapses when
per-frame motion drops below ~1 pixel; FFT-based phase correlation has
no such floor (sub-pixel via Foroosh-Zerubia closed-form).

## Why this experiment exists

After SAD trajectory regressed at 30 fps (s001/s002 sessions, build
#1123/#1124), we hypothesized that block-matching sub-pixel accuracy was
the bottleneck.  Phase correlation was prototyped on Linux against
`s083/bulk_gray.bin` and showed cleaner closure with sub-pixel detail
(s083/trajectory_phase_corr.png).  Ported to firmware:

1. CMSIS-DSP `arm_cfft_f32` length 64 added to `libs_CMSIS-m7` build,
   tables trimmed via `ARM_DSP_CONFIG_TABLES + ARM_TABLE_*_64` defines
   to fit the layout.
2. FFT code routed to SDRAM via new `.cmsis_dsp` linker section
   (`m_text` ITCM is too small).
3. `flow_phase_corr.cc` implements 2D FFT (separable row/col), Tukey
   window, per-frame mean removal, cross-power normalization,
   Foroosh-Zerubia sub-pixel.
4. `flow_task.cc` swapped `sad_match` for
   `sentai_flow_phase_corr_compute`.

## Crash isolation breadcrumb

Initial integration crashed at frame 73 (STACK_OVF, BFAR=0x666C6F77
"flow").  Root cause: `publisher_task` stack sized for SAD's flat call
tree (1.5 KB) was insufficient for `arm_cfft_f32` + radix4 + radix8 +
bitreversal2 nesting + 32 KB memcpy locals.  Diagnosed via a NOLOAD
SDRAM breadcrumb ring (`s_bc` in `.sdram_phase_corr_bc`) dumped at boot
in `app_main`.  Fix: bumped stack to 4 KB (`configMINIMAL_STACK_SIZE *
8`) with the crash dump as evidence.

The breadcrumb ring + boot-time dump are kept in the firmware as a
permanent diagnostic surface (per embeded.md F + I).
