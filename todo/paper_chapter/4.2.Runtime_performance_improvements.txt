4.2 Runtime performance characterization

This section characterizes the runtime performance of the final embedded vision configuration on the physical board. The measurements cover the standalone EdgeTPU invocation path, the complete camera-to-detection pipeline, multi-patch inference, and dual-camera operation. The purpose is to report the sustained behavior available to the onboard runtime, rather than isolated accelerator-only estimates.

All timing values in this section were measured on the embedded target using elapsed wall-clock time from the runtime microsecond timer. Throughput values were computed from complete operation intervals: a standalone invoke includes the USB input transfer, instruction transfer, output readback, and completion event; a pipeline output includes acquisition, preprocessing, EdgeTPU invocation, and publication of the detection result. Repeated pipeline measurements were taken after fresh boots to avoid residual state from previous runs. Visual camera-switch checks were used only to validate frame identity and were not included in timing loops when image serialization could perturb performance.

4.2.1 Measurement Summary

Table 8 summarizes the sustained performance of the final runtime configuration. The 512 x 512 YOLO workload reaches 24.50 standalone EdgeTPU invokes/s. When camera acquisition and preprocessing are included, the single-camera pipeline produces 23.44 detections/s. Multi-patch configurations preserve the requested number of invokes per frame, while total invoke throughput remains close to 24 invokes/s. Continuous dual-camera alternation at a 1:1 ratio reaches 14.39 combined detections/s, corresponding to 7.20 detections/s per camera.

Table 8. Measured runtime performance summary.

These measurements show that the effective performance is determined by the complete onboard data path: camera capture, memory movement, preprocessing, USB transfer to the EdgeTPU, result readback, and task scheduling. For the evaluated 512 x 512 workload, the EdgeTPU path sustains approximately 24 invokes/s, and the full single-camera pipeline operates close to that limit.

The standalone invoke loop isolates the USB-to-EdgeTPU path from camera acquisition and preprocessing. Each invoke sends a 512 x 512 x 3 uint8 input tensor, transfers the model instruction stream required by the EdgeTPU runtime, reads the output tensor, and waits for the completion event. Chunk size was varied to evaluate the effect of transfer granularity on sustained invoke throughput.

The tested chunk sizes produce similar results, all within a narrow band around 24 invokes/s. The fastest measured configuration uses 128 KB chunks, with an average invoke time of 40.813641 ms. Since a complete invoke takes approximately 41 ms, higher-level pipeline configurations that use the same model are expected to remain close to 24 invokes/s unless they reduce the amount of data transferred or change the EdgeTPU invocation pattern.

4.2.5 Dual-Camera Switching and Alternation

The dual-camera subsystem was evaluated using two complementary measurements. The first measures manual switching from one selected camera to the first usable tensor after the switch. The second measures continuous 1:1 alternation while the pipeline is running. These measurements answer different questions: manual switching captures the cost of changing the active sensor on demand, while continuous alternation reports the sustained rate when both cameras are sampled in a fixed schedule.

Table 13. Dual-camera timing and alternation measurements.
Scenario	Drain setting	Measured result	Content verdict
Manual select() -> to_tensor()	1	93.891 ms	valid
Manual select() -> to_tensor()	2	131.085 ms	manual timing only

Continuous ratio(1,1)	2	4.981067 detections/s combined, 2.490534 detections/s per camera	invalid for continuous alternation

For manual switching, the application-visible cost is the complete select() -> to_tensor() interval, not only the MUX selection step. With the one-frame drain setting, the first usable post-switch tensor is available after 93.891 ms on average. In continuous alternation, the one-frame drain setting is the validated configuration for the current scheduler. The two-frame drain setting is slower and was not content-correct under continuous 1:1 alternation.

Frame identity was validated with camera-specific patterns. In the controlled pattern, the left column is white for one camera and dark for the other. A correct frame has a uniform left-column signature matching its camera tag. This check detects stale, mis-tagged, or mixed frames without relying on human inspection alone.

4.2.6 Detection Update Periods

The measurements above support update-period claims for the current runtime. A complete photon-to-detection latency distribution would require a same-frame timestamp trace through image exposure, CSI transfer, preprocessing, invoke submission, invoke completion, post-processing, and publication. The present measurements instead report the output periods and switching intervals directly observed by the runtime.

Table 15. Measured and derived update-period quantities.
Quantity	Value	Source
Single-camera detection output period	42.654 ms	derived from 23.444330 detections/s
Standalone EdgeTPU invoke time	40.813641 ms	measured complete invoke timing
Continuous 1:1 combined output period	69.479 ms	derived from 14.392763 detections/s

In single-camera operation, the runtime publishes detections every 42.654 ms on average. In continuous dual-camera alternation, detections are produced every 69.479 ms overall, while each camera is refreshed every 138.959 ms on average. These values are the appropriate performance quantities for control loops that consume the published detections.

4.2.7 Summary

The final platform sustains real-time onboard vision with a 512 x 512 YOLO model on the EdgeTPU while running the complete embedded camera and preprocessing pipeline. Standalone EdgeTPU execution reaches 24.50 invokes/s, and the full single-camera pipeline reaches 23.44 detections/s with no timeouts or inference failures in the repeated measurements. Multi-patch operation maintains approximately the same total invoke throughput while trading frame rate for multiple detections per frame. Continuous dual-camera alternation is stable and content-correct at 14.39 combined detections/s with the validated drain=1 setting.

These results show that the useful performance of an MCU-class EdgeTPU vision system is defined by the complete onboard chain, not by accelerator execution in isolation. The limiting factors include tensor transfer, instruction transfer, camera scheduling, memory placement, preprocessing, and synchronization. Reporting complete-operation wall-clock measurements therefore provides the most relevant characterization for embedded autonomy workloads.
