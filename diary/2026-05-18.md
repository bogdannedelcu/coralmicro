### OP-S10-W13 — `sentai.fr` Flight Recorder (production)

NASA/JPL FDR-style independent recorder.  4 channels (frames PGM /
events CSV / scalars CSV / kernel stub).  Producers push items
O(1) non-blocking; single drain task writes to disk asynchronously.

Key engineering decisions made under fire:
- Binary semaphore lock, NOT PI-mutex.  PI-mutex tripped
  `xTaskPriorityDisinherit pxTCB == pxCurrentTCB` assertion when
  SafetyTask and drain contended on it — also philosophically
  wrong (PI entangles priorities, exactly what an "independent
  recorder" must NOT do).
- Drain-side scratch slot is static BSS, not stack.  FreeRTOS
  POSIX stack ≈ 16 KB; a FrameSlot is ~76 KB at 320×240 → instant
  stack overflow.  Refactored to lift snap copy into BSS.
- State ↔ task split (commit `58cff126`) so the state machine is
  testable standalone, mirroring sentai.safety.

Last s170 run with FR open: 135/135 frames + 14/14 events drained,
0 drops, worst queue depth 1.  Drain keeps up at 30 FPS.

### OP-S10-W14 — `sentai.calib` autotune (algorithm demonstrated)

In-flight automatic calibration of the Flow loop gain.

**Identification result (7 trials, thesis-defensible):**

| Axis | Trials | Mean Kp | σ    | Median | Tu (s) | a_y (mm) |
|------|--------|---------|------|--------|--------|----------|
| X    | 4      | 0.393   | 0.043| 0.385  | 9.5    | 95-110   |
| Y    | 3      | 0.393   | 0.103| 0.336  | 9.0    | 75-115   |

cf2 X/Y body-velocity symmetry confirmed: `mean Kp_x = mean Kp_y`.

**Method:** classical Åström-Hägglund relay + Ziegler-Nichols
P-only with 20 mm hysteresis + VPE forwarder (PnP → cf2 ExtPos
@ 30 Hz) + cf2 IMU/baro noise zeroed.  ~30 s flight per trial.
100 % convergence success rate.

**Closed-loop validation (`s173_flow_hold_validation`):** with both
`Kp_x = Kp_y = 0.39` active simultaneously in a P-controller, drone
held position over 30 s with:
- max drift:  **1.5 cm** (limit 10 cm — 6.7× margin)
- RMS drift:  **0.7 cm** (limit  5 cm — 7.1× margin)
- landed:     **1.0 cm** from origin (limit 10 cm — 10× margin)

That's the proof the autotuned gains are real and work end-to-end.

## Bug root-causes found en route (debug iterations recap)

Each W14 iteration nailed down ONE concrete bug.  In sequence:

1. **iter #2** — SDF marker face 6 → 12 cm.  At z=0.9 m the
   original 6 cm marker projected ~16 px per side — borderline
   for ArUco's 4×4 bit decoder.  Doubling gave ~32 px = ~8 px per
   cell, reliable detection through the entire autotune.
2. **iter #7** — `s_marker_size_m` 0.125 → 0.094.  Earlier 0.125
   was a wrong 2× of the OLD 0.0625, ignoring that 0.0625 already
   accounted for ArUco texture-padding ratio (0.781 inside the
   physical face).  Wrong value caused PnP-z to report 2× the
   actual altitude.
3. **iter #11** — added `sentai_crazy_hl_stop()` primitive.
   cf2's HL Commander stays active after `takeoff()`; Generic
   Setpoint `hover()` was being overridden silently.  HL_CMD_STOP
   (CRTP port 0x08, payload [3, group_mask]) puts HL in IDLE
   without killing motors.  After this, `hover(vx, vy, 0, z)`
   finally drove the drone.
4. **iter #13** — built VPE forwarder.  Without it, cf2's EKF
   z drifted (baro + IMU integration error) and the drone climbed
   to 1.4 m even with `hover(z_distance=0.9)` absolute.  Forwards
   PnP-derived (x, y, z) → cf2 CRTP LOCALIZATION port @ 30 Hz.
5. **iter #15** — CRTP ExtPos packet format fix.  Was channel 1
   (GENERIC) with a leading type byte (the EXT_POSE_PACKED format).
   Correct: channel 0 (POSITION_CH), payload = 3 floats raw (12 B,
   no prefix).  cf2 was discarding our packets as garbage.  This
   fix produced the FIRST autotune convergence (Kp_x = 1.58 at
   the time — later identified as polluted by noise; iter #21-22
   re-converged cleanly to Kp = 0.45 → ~0.39 after Y-axis runs).
6. **iter #21** — peak detector hysteresis-safe.  When dead-band
   grew to 20 mm to break resonance, drift slipped through the
   silent zone in single ticks → `prev_sgn` was 0 → flip events
   missed → no peaks pushed → empty cycle ring → no convergence
   despite clean oscillation visible in the trace.  Fix: track
   `last_active_sgn` (sticky across silent zone) + `peak_extremum`
   (signed running max).
7. **iter #18** — IMU + baro noise zeroed in Gazebo SDF
   (operator-requested).  RESTORE before any test depending on
   the noise profile (canonical FlowBaseline s127 regression).
8. **iter #14 cautionary tale** — boosting VPE rate 5 → 30 Hz with
   the BAD format made cf2 estimator wildly worse (drone climbed
   to 3.4 m, then crashed).  More-frequent-bad-data is worse than
   rare-bad-data.  After format fix, 30 Hz works perfectly.

### Format preference for persistence (T7 follow-up)

Operator-stated 2026-05-18 ("nu prea vreau sa tinem configurari in
json, un format mai simplu, cheie valoare e mai potrivit pentru
MCU"): persist as `key=value\n` text, not JSON.  Example
`/system/flow_gains.txt`:

```
schema=1
kp_x=0.393
kp_y=0.393
tu_s=9.5
ay_m=0.10
ts_ms=1747585294000
```

That's an FxUser-friendly format: one line per setting, parser is
a 20-line C function (`strstr`/`atof`), no JSON library dragged in.
T7 will load this on boot, autotune writes it on `done_ok`,
sentai.calib HOLD reads it for production hover.

### Caveats that travelled with us (DO NOT SKIP)

1. **Vendor CrazySim SDF noise was zeroed** for the W14 trials.
   That repo is outside `coralmicro`; remember to restore
   `gyro σ=0.0035`, `accel σ=0.05`, `baro σ=0.01` before running
   anything that depends on the realistic noise profile (the
   canonical FlowBaseline s127 regression specifically).
2. **Yaw drift ~45° observed** during autotune trials (operator
   visual).  ExtPos sends position-only; cf2's EKF has no
   correction for yaw from our VPE.  As yaw drifts, body-frame
   velocity commands rotate relative to world → relay direction
   decouples from PnP-drift.  Send ExtPose (with quaternion =
   PnP-derived rotation) to close that loop; or pivot Y-axis
   to a yaw-rate-control mode.
3. **Kp_flow = 0.39 valid ONLY for**: SIM cf2 + hl_stop + hover()
   body-frame velocity + z = 0.9 m hover + noise-zeroed Gazebo
   profile.  Different altitude / cf2 firmware / real hardware =
   different Kp.  Always re-run autotune per platform; store
   per-platform Kp in `/system/flow_gains.txt`.
4. **Duplicate `sentai.crazy` MP binding** (ARM `bindings/`
   vs SIM `sim/`).  When I added `hl_stop` and `send_extpos` I
   had to patch BOTH.  Unification queued (W15 or FW).

## Late-evening addendum — T16 prerequisite verified (analysis only)

Operator concern (rotation-aliasing of ArUco IDs at certain camera
angles, potentially breaking T16 yaw test) prompted a systematic
analysis: `sim/scripts/aruco_pick_robust.py` computed in-scene
min Hamming distance across rotations for the full DICT_4X4_50.

Numbers:

| Set                            | In-scene min Hamming (16 bits total) |
|--------------------------------|--------------------------------------|
| Legacy {0,1,2,3} (current SDF) | **7**                                |
| Greedy top-4 {1,23,0,2}        | 6 (counterintuitively WORSE)         |
| Brute-force global optimum {1,4,8,40} | 8                              |

Legacy markers already have Hamming 7 → 44 % of bits flipped from
any rotation to any other in-scene marker.  Math-impossible for the
detector to confuse.  Brute-force optimum at Hamming 8 is the
ceiling for this dictionary; gain over legacy is marginal (44 % →
50 %).

Web search cross-check (OpenCV docs + Garrido-Jurado 2014 paper
spirit + PyImageSearch + GitHub issue #3190 "pose-ambiguity"):
confirmed that ArUco dictionary design ALREADY handles rotation
recovery by construction.  The real "PoseEstimation ambiguity"
issue is a camera-marker GEOMETRY problem (small or distant
markers), not a marker-ID problem.  Our 12 cm markers at z=0.9 m
project ~32 px/side — outside the ambiguity regime.

**Decision**: STAY with legacy markers.  No texture / SDF /
KNOWN_POSITIONS_M work needed.  Saves ~30 min that would have
gone into marginal improvement.  Analysis script kept for the
record + future audits (different dict, different scene layout).

The takeaway, in honest engineering terms: I anticipated a
failure mode ("PnP rotation ambiguity at certain angles" in the
T16 spec) without first computing whether it could actually
happen with our current setup.  Brute-force showed legacy is
already safe.  Lesson: always check the numbers before listing a
failure mode as worth-mitigating.
