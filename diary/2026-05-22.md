## Iteration grind — 23 iters today on s190

Critical findings, in order:

### Iter-1..2: bridge path + spawn flake
- `gz_to_uds_bridge` was looked-up at wrong path (`build-sim/sim/gazebo/`
  instead of `build-sim/sim/`) — camera frames never reached
  sentai_sim.
- `launch_hybrid_cf2.sh` had `sleep 4` after gz sim and `--timeout
  300ms` on spawn — too tight.  Spawn intermittently failed.
- Fix: longer sleep (4→8 s) + retry spawn up to 3× / 5 s timeout each.

### Iter-3..5: PnP-z perspective bias
- Drone took off + markers detected, but PnP-z returned wildly wrong
  values (e.g. 0.005 m when drone was at 1.5 m real).
- Root cause: mission called `coplanar_pnp(img_pts, wld_pts)` with
  pixel/world correspondences **in wrong order** — WhyCon detection
  order is scan-order (unstable across frames), while MARKER_WORLD is
  canonical NW/NE/W/E/SW/SE.
- Fix: use `sentai.markers.get_drone_pose_tuple(yaw)` which does
  internal permutation-search + Kabsch + yaw-anchor mirror picker
  (shipped W19-T6b).  Now PnP-z reasonable (0.33–0.40 m at handoff).

### Iter-6..9: bindings + frame inspection
- `bytearray` not in MicroPython embed — use `bytes` concat from
  `struct.pack`.
- `sentai.fr.open(name, path)` takes string channel name ("frames"),
  not enum int.
- Saved frames via `sentai.fr` and visually inspected → confirmed
  operator's claim: markers visible at 0.3–0.5 m **real** altitude,
  not 2 m+ (the `ekf_z` reading was inflated ×10 from IMU integration
  drift, not real altitude — cf2 has no Z source).

### Iter-10..13: lift control
- Drone climbed too fast through the marker-visible band (1-2 frames
  with markers, then drone exits at top).
- Tuned T_MAX 45000 → 40000, RAMP_S 3→6, but drone still overshot
  (peak GT z = 2.5 m vs target 0.5 m).
- Operator visual feedback: "decolarea se face prea repede".

### Iter-14..21: PD altitude controller via vision
- Realized: this is the classic quadrotor altitude PD problem
  (Bouabdallah 2004, Mahony/Kumar/Corke 2012).
- Pulled physics from `model.sdf.jinja`:
  - m = 0.0282 kg (base + 4 props)
  - F_max = 0.676 N (4 × motorConstant × maxRotVelocity²)
  - F_hover = 0.277 N (m·g)
- Derived Kp/Kd from desired closed-loop dynamics
  (ω_n=1.5, ζ=0.8): Kp ≈ 6000, Kd ≈ 6000 units/m & units/(m/s).
- Iter-19: added LPF on PnP-derived velocity (α=0.25) — PnP
  frame-to-frame jitter caused spurious vz=1.25 m/s when real was
  0.3 m/s.
- Iter-20: stability check uses **vz-only** (not |err_z|) — drone
  stabilizes at WHATEVER altitude vision found markers, HL go_to
  handles the rest.
- Iter-21: warmup phase **continues PD logic** (was jumping thrust
  from PD's stable ~32500 up to fixed T_HOVER=36500 → drone
  re-accelerated +0.16 m during warmup).  Now thrust evolves smoothly.

**Iter-21 GT peak z = 0.91 m** (down from 2.52 m in iter-15 / 1.51 m in
iter-13).  Operator visually confirmed "e perfecta decolarea, se
stabilizeaza foarte bine".

### Iter-22..23: bringup orchestrator engages but SAMPLE → SAFETY in 7 s
- Operator: "după o secundă de stabilizare începe să driftuiască pe Z
  foarte mult, ca și cum datele de calibrare sunt greșite".
- Diagnostic ticks added: marker count + cf2 EKF pose every 100 ms
  during bringup.
- **n_cache = 0 in ALL 71 ticks** — markers never re-detected after
  handoff.
- **cf2 EKF pose IDENTICAL byte-for-byte** for 7 s — pose updates
  frozen, suggesting cf2 stopped processing inputs.

### Root cause: cf2 SITL packet queue overflow
- cf2.log: **13312 packets dropped (52 log entries × 256)**, sustained
  ~530 drops/sec.
- ESTKALMAN warnings: "Kalman prediction rate off (94)" — cf2's main
  thread is CPU-bottlenecked.
- Source budget:
  - Gazebo plugin: IMU @1000 Hz + baro @50 Hz = **1050 pkt/s**
  - Mission: RPYT @30 Hz + ExtPos @30 Hz = **60 pkt/s**
  - Bringup orchestrator: hover @10 Hz + ExtPos @10 Hz = **20 pkt/s**
  - **Total: ~1130 pkt/s**
- cf2's socketlink queue is 2000-deep; drain rate ~600/sec under
  load.  Net: 500 drops/sec sustained.
- ExtPos packets are part of the dropped set → Kalman never gets new
  position observations → EKF freezes → cf2 controller commands
  wrong → drone falls.
