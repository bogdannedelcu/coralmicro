### Lane A follow-up: T18-T SIMD attempt (CLOSED net loss)

Spent ~90 min attempting to math-identically speed up the
Bradley adaptive threshold (`aruco_adaptive_threshold`).  Three
variants tried, all measured **net loss** on the cycle bench:

1. C-level refactor (per-column LUTs + division elimination via
   `(gray+C+1)*box_area <= box_sum` algebraic identity).  Math
   identity verified byte-perfect on 5 block sizes (7..201) over
   the canonical synth frame, both ARM and SIM.  Measured **24 %
   SLOWER** on M7.  gcc -O2 was already hoisting per-row invariants
   and converting the divide to multiply-by-reciprocal; LUT loads
   added 3 cacheable hits per pixel that broke pipelining.

2. ITCM placement via `__attribute__((section(".ramfunc")))` on
   the same function.  Measured **16 % SLOWER**.  Function-call
   overhead from breaking inlining outweighed the per-fetch ITCM
   win on an 870-byte kernel.  ITCM region landed at 0x00000c00
   length 0x368 (confirmed via `arm-none-eabi-objdump -h`).

3. 32 B cache-line alignment of all hot ArUco buffers (s_binary,
   s_labels, s_integral, s_fill_stack) via `aligned(32)` in
   ARUCO_BSS_ATTR.  No measurable delta — within noise.  Kept
   anyway as it codifies the OP-S10-W15 alignment policy and
   costs nothing.

**Kept as useful infrastructure**:
- `sentai.aruco._verify_threshold(block)` — runs scalar reference
  vs production threshold on a deterministic synth frame, returns
  mismatch count.  Any future Phase-2 refactor MUST keep this at
  0.  Validates byte-identity in <50 ms.
- `sentai.aruco._thresh_cycles()` — last (old, new) cycle pair
  for cycle-level perf regression checks.
- Lessons-learned comment block in `sentai_aruco.cc` above
  `aruco_adaptive_threshold` so the dead ends don't get
  re-discovered next session.

**Honest verdict**: Bradley adaptive threshold is already well-
optimized by gcc -O2 on Cortex-M7; further wins need either
explicit CMSIS-DSP intrinsics in the inner loop
(`OP-S10-W14-T18-U`, ~1-2 days) or an algorithm shift to a
non-equivalent threshold (PXP path, 5.8 × at the cost of math
identity — rejected by operator).  Production stays at 24 ms /
detect (72 % of 30 FPS frame budget) — enough headroom for now.

### Lane A follow-up #2: T18-U CMSIS-DSP intrinsics (modest win shipped)

Operator pushed back on the "stop at 24 ms" verdict: validate
ARM viability with real CMSIS-DSP before reducing scope.  Spent
~60 min on the explicit-intrinsic path; final result is a real
but modest win.

**Code shipped** (build #1353):
- The `gcc 9.3` toolchain in `third_party/toolchain-linux/` does
  NOT ship `__USUB8` / `__SEL` in its `arm_acle.h` (only `__USAD8`
  / `__USADA8` are exposed).  Wrote two-line `aruco_usub8` /
  `aruco_sel` inline-asm wrappers verbatim from
  `third_party/CMSIS/CMSIS/Core/Include/cmsis_gcc.h`.
- Phase 2 split: left-border scalar (clamped) → SIMD interior
  4-wide compare (divide-eliminated via the algebraic identity
  `(gray + C + 1) * box_area <= box_sum`) → tail scalar → right-
  border scalar.  Interior covers 37.5 % of pixels at block=201
  (where `x_factor = block`).
- All hot buffers carry `aligned(32)` for the M7 D-cache line
  (OP-S10-W15-T5 policy preview).

**Measured**:
- End-to-end detect: 24 ms → **22 ms** (median over 30 iters;
  σ ≈ 0.4 ms; min=22, max=23).
- Byte-equivalence: 0 mismatches on block ∈ {7, 23, 51, 101, 201}
  versus the scalar reference.  Math identity preserved.
- Frame-budget utilisation @ 30 FPS: 72 % → **66 %**.
- Equivalent FPS: 41.7 → **45.5**.

**Why not more**: at production `block=201` the interior region
is only 120 / 320 cols = 37.5 % of pixels.  Border 62.5 % stays
scalar (per-pixel varying `x_factor`).  Cycle-bench inside
verify shows scalar_ref slightly faster (it's inlined into the
single-call-site verify; production path which has multiple
callers does NOT get inlined → SIMD wins the inlined
comparison too).  Phase 1 (serial integral-image build) is the
next limiter and is intrinsically hard to vectorise on M7 (no
parallel prefix-sum primitive).

**ARM viability for this thesis is VALIDATED**: 22 ms per
detect frame, 45 FPS equivalent, math-identical to reference,
runs on real Coral Dev Board Micro hardware.  Further reduction
parking-lot: T18-V (PXP path, ~10 ms detect, algorithm-non-
identical) — only if a subsystem squeezes the per-frame budget
later.

### Budget sanity check — concurrency analysis

After T18-U landed, operator asked the right architectural
question: 22 ms is CPU time on a single core; can the algorithm
parallelise, or does it block everything else?

**Audit results** (code review 2026-05-19):

- **Cortex-M4 is currently idle.**  `CMakeLists.txt:253-256`
  explicitly removed the M4 build target at build #1130+
  citing "M4 had unreliable SysTick + freeze under load".
  Flow SAD that operator initially recalled as running on M4
  is actually on M7 (`flow_task.cc:14` header comment confirms
  single-core M7).  `flow_task_m4.cc` is kept as historical
  reference but not compiled.
- The Cortex-M4 on RT1176 **does** have a single-precision FPU
  (M4F per NXP datasheet) — the recall that "M4 has no FPU"
  was wrong; the real M4 blocker was SysTick reliability.
- **Single source of truth for ArUco compute**: only
  `SafetyTask` calls `sentai_aruco_detect()` live in C
  (`sentai_safety_task.cc:190`).  `sentai_calib_task.cc:6-7`
  header is explicit: *"REUSE ONLY (no duplicate compute):
  sentai_aruco_get_latest() — cached PnP markers"*.  Autotune,
  VPE forwarder, and mission scripts piggyback on the cached
  result; they never re-run detection.  Nice design discipline.
- So the M7 budget pressure is dominated by **one knob**:
  `SENTAI_SAFETY_TASK_PERIOD_MS` (currently 33 ms = 30 Hz
  nominal).  At 22 ms detect per call, that's ~66 % M7 just for
  SafetyTask.

**Subtle CMake-parsing gotcha worth remembering**: the
`add_executable_m7` macro uses `DATA` as a multi-value keyword
(eats arguments until the next keyword).  M4_EXECUTABLE + DATA
MUST go AFTER the source-file list, not before — placing them
first silently consumes the source files as data items and the
M7 link fails with "undefined reference to app_main".  Fixed by
moving the M4 block to the bottom of the source list (matching
the historical build-#1130 pattern).

### M4 bench wiring attempt + blocker (build #1357, #1358)

After committing the SIMD ArUco + M4 groundwork, pushed the
runtime wiring:

- `examples/sentai_runtime/m4_bench_host.cc` — M7-side driver
  that calls `IpcM7::GetSingleton()->StartM4()`, fills a
  synthetic 80×60 gray frame at the shared mailbox, kicks the
  go flag, polls for done, returns the DWT cycle count.
- `sentai.diag.m4_aruco_bench(block)` MP binding exposing the
  above as `{ok, alive, cycles, us, frame_w, frame_h}`.
- Both sides agree on mailbox base 0x202C2000 (inside the M4
  linker's rpmsg_sh_mem region, past IpcM7's ~400 B of queue
  storage at the start).

Flashed build #1358 — `alive=0`, `cycles=0` for all block
sizes (7..201).  M4 boots (no crash from M7 side) but the
magic word never appears at the M7's view of 0x202C2000.

**Root cause of the silence** (found via the linker scripts —
not a code bug, an architecture trap):

M7's `MIMXRT1176xxxxx_cm7_ram_mp.ld` and M4's
`libs/nxp/rt1176-sdk/MIMXRT1176xxxxx_cm4_ram.ld` disagree on
both the address AND the size of `rpmsg_sh_mem`:

| Core | `rpmsg_sh_mem` ORIGIN | LENGTH |
|------|----------------------:|-------:|
| M7   | `0x2033E000`          | `0x2000` (8 KB) |
| M4   | `0x202C0000`          | `0x4000` (16 KB) |

My hardcoded 0x202C2000 falls inside M7's regular `m_ocram`
(0x20240000-0x2033E000), which is **cacheable** from the M7
side.  M7's D-cache happily serves stale zeros for the magic
read.  Even if M4 is writing the magic word correctly, M7
never sees it.

These two addresses on RT1176 likely alias to the same physical
OCRAM region through different bus-matrix paths (NXP-specific
OCRAM_M7 / OCRAM_M4 aliases per the i.MX RT1170/1176 reference
manual), but to share state cleanly we MUST place data in the
`.noinit.$rpmsg_sh_mem` linker section on both sides — that's
how the existing IpcM7 tx/rx queues survive.  Hardcoded
pointers to "an address in the middle" don't work.
