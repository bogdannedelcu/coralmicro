## My viewpoint

1. **This is a real step forward.**  We can now publish
   "WhyCon centroid p95 = 1.51 px, pose RMSE = 16 mm on a 368-frame
   synthetic Gazebo dataset" with ablation-grade backing.  Before
   this work the only WhyCon metric was a closed-loop drift number,
   which bundled detector + EKF + PnP + control + CRTP + Gazebo
   physics into a single failure.  That bundle is now decomposable.

2. **The 22-May "detector recall bug" hypothesis was right.**  T13
   iter-21d (bit-perfect threshold + RETR_EXTERNAL gap) was on the
   correct trail.  The helper extended it correctly: the under-count
   was *primarily* an OpenCV-vs-embedded contour-vs-CC semantic
   mismatch, not a threshold tuning issue.  Resolution: drop W3,
   move both implementations to the same CC + concentric ring/dot
   structure, validate visually first, claim parity only after
   recall numbers AND geometry numbers (centroid + radius + axes)
   agree.  Good methodology.

3. **Pose ambiguity is the real next problem, not detector recall.**
   On a 6-marker symmetric layout 45 / 75 pose frames had a
   near-ambiguous IPPE/permutation alternative.  The asymmetric 7th
   marker helps but does not eliminate it — any frame where only a
   weak 4-marker subset is visible can still mirror-branch.  This
   is consistent with the closed-loop "PnP bimodal" symptom from
   s191 iter-15..18.  The validator now exposes ambiguity as a
   diagnostic, but flight code needs prior-guided assignment (prev
   pose + yaw/IMU prior + Hungarian on projected NN + residual
   early-rejection).  Spec is already in B2 §"Runtime Pose
   Assignment Options"; we need to fold it into `sentai.markers.
   get_drone_pose_tuple` properly.

4. **sentai_sim FP=19 across 368 frames is the next focused
   debugging target.**  False positives can mask misses if a
   spurious detection lands within match-threshold of a true marker.
   Need to inspect: are the 19 FPs ground-texture artefacts at
   z=1.00 m?  Re-tune the small-dot pairing gate, but do it on the
   dataset bench, not in flight.

5. **`edge_partial` is a labeled variant, not the parity baseline.**
   The helper correctly resisted folding cropped-marker recovery
   into default metrics: cropped markers are `partial_crop`
   manifest stress cases, not the parity ground truth.  Keeping
   `edge_partial` as a separate named OpenCV variant is the right
   call.  If we want cropped-marker recall in flight, port
   `edge_partial` to sentai_sim *as a labeled variant* and rerun
   ablation — don't bolt it into the production path silently.

6. **Anti-cheat status: clean.**  Sentai consumes only camera
   frames (320×240 grayscale PGM = same encoding the embedded
   pipeline gets from `gz_to_uds_bridge`); manifest ground truth is
   used only host-side in the validator, not piped into sentai_sim.
   Per `[[feedback-sentai-sim-air-gapped-from-truth]]` this is by-
   the-book.  Contrast with yesterday's `SENSOR_TOF_SIM` plugin
   patch (now backed out per the 22-May plan).

7. **Uncommitted work needs landing.**  `git status` shows the C++
   detector rewrite, the new ABI, the binding, the QSTR diff, and
   sim build-version bump are all still uncommitted.  Build #558+
   is what produced the 368-frame numbers above, so the binary
   exists but the source isn't recorded yet.  Risk: another grind
   session on s191 will rebuild from the last committed state
   (6381b7e7) and lose the parity port.  Need to commit
   under a fresh task code before doing anything else.

### s193 — full calib bringup, 18 iters of pain

Cloned s187 + added 7-marker pad (whycon_N injected into upstream
`sentai_whycon_small.sdf`, logged in `ideas/external_patches.md`).
The actual calib path — `sentai.calib.run_bringup()` — kept failing.

#### Major findings

1. **HL takeoff doesn't work without baro / TOF / flow_deck.**
   cf2 Kalman has no Z source pre-flight → integrates IMU → Kalman
   reports false altitude → drone doesn't physically lift.  s193
   iter1 demonstrated this: ekf_z ramped 0→4 m while GT z=0.015 m.
   Same chicken-and-egg s190 documented 22-May.  Fix: Classic
   RPYT thrust ramp (proven in s192).

2. **HL go_to() with planner.state==IDLE → trajectory NaN crash.**
   Traced in firmware source: `planner.c:106 plan_current_goal`
   returns `traj_eval_invalid()` (= `pos = vrepeat(NAN)` per
   `pptraj.c:280`).  Then `plan_go_to_from(curr_eval=NaN, ...)`
   computes polynomials from NaN → setpoint NaN → motor commands
   undefined → yaw spike + crash.  Hit reliably iter4-iter12.
   Fix: replace `go_to()` with `takeoff()` for handoff.
   `plan_takeoff()` reads cf2 Kalman state explicitly in the CRTP
   handler → trajectory starts from a valid position.
   iter13 confirmed the fix: drone stable through handoff for the
   first time (z=0.67 m yaw=0° during phase 5).

3. **PnP yaw = ±90° is CORRECT, not a mirror bug.**  Misdiagnosed
   initially.  SDF GT `R_cam_to_body=[[0,1,0],[1,0,0],[0,0,-1]]`
   means the camera mount is rotated 90° wrt body frame.  PnP
   reports drone yaw relative to PAD world, which differs from cf2
   gyro yaw (which is relative to drone initial heading) by
   exactly this mount rotation.  Rejecting PnP based on
   pnp_yaw ≠ cf2_yaw breaks calibration (operator-corrected).

4. **iter17/18 — RPYT-based axis ID before handover (operator
   architecture).**  Drone stays in proven-stable RPYT throughout
   axis identification.  Body+pitch pulse + body+roll pulse, each
   with brake + settle + PnP capture.  Compute body axes in pad
   from displacement vectors, commit_R, THEN handover.  iter17:
   axis_id_rpyt RAN, R committed (theta_p=155°, theta_r=136°,
   rc_commit=0), handoff succeeded, SAMPLE started.  Math for R
   still rough — drift between pulses contaminates displacement
   vectors → R isn't fully orthogonal.  Need better algorithm (or
   accept that orchestrator's SAMPLE+KABSCH refines from the rough
   initial guess).
